# Dry run: guesses and conflicts in PLAN.md

Executor dry run, no files touched except this one.

1. **Dead branch in the chip clamp.** Decision 1 / File changes says `const cv = v == null ? -1.5 : Math.min(-1.5, v);`. Inside computeProfile's stage loop (site/js/engine.js line 93) `v` is already checked with `if (v == null) continue;` before the chip loop at line 99-103 runs, so `v` can never be null when `cv` is computed. Proposal: write `const cv = Math.min(-1.5, v);` and drop the null branch, or say plainly it is defensive and why.

2. **Told-complaint ordering is only defined for 3 of 10 chips.** Screens 4 and 6 order testers by "the tester whose family carries the highest weight in that chip's family map," default woody amber, white musk, vanilla. In site/js/data.js lines 71-80, only `sweet` (vanilla_gourmand .8), `chemical` (woody_amber .9) and `soapy` (white_musk .7) put nonzero weight on a tested family; `powdery`, `heavy`, `smoky`, `animalic`, `sour`, `loud`, `faded` all score 0 on all three testers, so the stated rule gives no order for 7 of 10 answers. Proposal: state that a zero-weight chip falls back to the full default order, and write that into quiz.js rather than leaving it implicit.

3. **build_artifact.py is told two different things about quiz.html.** The site/quiz.html bullet keeps "ARTIFACT markers" like index.html; the tools/build_artifact.py bullet says quiz.html is "handled like articles.html." In tools/build_artifact.py, the index.html path (lines 13-16) requires exactly two `<!--ARTIFACT:START-->...<!--ARTIFACT:END-->` blocks and fails with SystemExit otherwise; the articles.html path (lines 27-32) extracts `<head>`/`<body>` by regex and never looks for those comments. If quiz.html keeps the markers but is processed the articles.html way, they become dead markup; if it is processed the index.html way, it needs exactly two marker pairs instead of a full head/body. Proposal: drop the ARTIFACT markers from quiz.html and add a third head/body block to build_artifact.py that mirrors the articles.html block.

4. **articles.html has no nav to add a link into.** site/articles.html lines 35-43 show a header with only `brand` and the language toggle, no `<nav class="topnav">` (that wrapper exists only in site/index.html line 25). The plan's file-changes bullet assumes both pages get a nav link the same way. Proposal: E3 decides whether quiz.html's link goes in a new nav wrapper or beside the existing `back` link, and touches site.css only if a wrapper is added.

5. **articles.html's own T object has no nav slot at all.** Its inline script (site/articles.html lines 56-64) defines `brand, h1, lede, back, foot, articles` and nothing that renders nav text; there is no `navArticles`-equivalent key to extend the way app.js's `T.navArticles` works. Proposal: add a `navQuiz` key (English and Arabic) and a line setting it, mirroring how `back` is already set.

6. **`?add=<id>` races the lazy catalogue.** `addPerfume` (site/js/app.js line 409) only fires for `byId[id]` (verified) or `AUTO[id]`; `AUTO` is populated only inside `loadCatalogue()`'s async fetch callback (lines 224-232), which resolves after the synchronous `renderAll()` at load (lines 498-500). A quiz result linking to a non-verified id via `index.html?add=<id>` will silently do nothing if the fetch has not returned yet. Proposal: retry the `?add=` id once `loadCatalogue()`'s promise resolves, not only once at top-level load.

7. **No concrete data attributes or classes for the new step machine.** The quiz.js and site.css bullets never name the attributes for tile selection, verdict options, the "when did it bother you" options, narrowing tiles, told/anosmia options, or Continue. Since the one shared click listener (pattern at site/js/app.js line 450, `ev.target.closest("button, a")`) only catches real `<button>`/`<a>` elements, every one of those must render as a button, not a styled div. Proposal: fix the attribute names (e.g. data-tile, data-verdict, data-when, data-told, data-anosmia, data-narrow) before E3 starts, and confirm each sits on a `<button type="button">`.

8. **tests/lib/dom.js cannot query the DOM beyond `[data-add]`.** Document-level `querySelector` always returns null (line 35); the element-level one only recognizes the literal string `"[data-add]"` (line 22). tests/quiz.test.js cannot use any DOM query to find "every offered narrowing tile"; it must regex the raw innerHTML from `page.snapshot()`. Proposal: state in the tests section that narrowing-tile checks are done by regexing snapshot HTML, not by a query helper, and confirm quiz.js's own logic never calls `document.querySelectorAll`.

9. **`page.input`/`page.key` are hardcoded to id "q."** tests/lib/dom.js lines 94-95 call `byId("q")` directly, so quiz.html's search box must keep `id="q"` and must be the only element with that id on the page (matches the plan). Proposal: no change needed, but flag it so E3 does not add a second search-like input (e.g. inside narrowing) reusing "q."

10. **Which stage a verdict's chips attach to is not pinned down.** Test 2 expects `{opening: null, heart: null, drydown: -2, chips: {drydown: ["chemical"]}}` for a "turned on me / hours later / chemical" answer. The verdict table (Verdict mapping) maps "when did it bother you" to a stage but never states that the chosen chips must be written under that same computed stage rather than a fixed one.
